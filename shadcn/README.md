# shadcn-агенты

Агенты для проектов, где UI собирается из **готовых компонентов registry-библиотек** — shadcn/ui и совместимых реестров (@magicui, @originui, @aceternity, @cult-ui и ещё три десятка). Они НЕ входят в обязательный пайплайн основного набора: ставятся только если проект действительно работает с такими библиотеками.

| Agent | Роль |
|-------|------|
| `shadcn-requirements-analyzer` | Требования/UX-план → проверенный список компонентов, дерево иерархии, состояния, `ui-requirements.md` |
| `shadcn-component-researcher` | Глубокий ресёрч реестров: исходники, props, примеры (валидация/загрузка/ошибки), команды установки → `ui-components-research.md` |
| `shadcn-implementation-builder` | Сборка production-кода из компонентов библиотеки: композиция, типизация, состояния, валидация, доступность, адаптивность |
| `shadcn-quick-helper` | Быстрая справка по одному компоненту: команда установки + базовое использование + ключевые props. Вне пайплайна |

Плюс два файла-ресурса, которые ставятся в проект, а не в `.claude/agents/`:

| Файл | Куда в проекте | Зачем |
|---|---|---|
| `components-library-rule.md` | `docs/shadcn/components-library-rule.md` | Какая библиотека приоритетна и правила «готовые блоки → компоненты → кастом». Читается ВСЕМИ четырьмя агентами первым шагом |
| `registries.json` | `docs/shadcn/registries.json` | Справочник 34 реестров и их URL |

Все четыре агента — самодостаточные файлы формата `.claude/agents/` (frontmatter + промпт), как и основной набор.

## Пайплайн

```
@designer (проектирует экраны и флоу — как обычно)
  → @shadcn-requirements-analyzer   (маппинг на компоненты, иерархия)
  → @shadcn-component-researcher    (что реально есть в реестрах: API, примеры, установка)
  → @shadcn-implementation-builder  (сборка кода)
  → @code-reviewer → @security-reviewer → @qa-engineer → @devops

Вне пайплайна: @shadcn-quick-helper — «нужен date picker прямо сейчас»
```

Артефакты по фиче ложатся рядом с её планом: `docs/backlog/NNN-feature-name/ui-requirements.md`, `ui-components-research.md`, `ui-implementation.md`.

## Граница с `frontend-developer` — прочитай до установки

Это главный вопрос при интеграции: `shadcn-implementation-builder` и `frontend-developer` оба пишут UI. Граница зафиксирована в промптах обоих направлений:

| Зона | Кто |
|---|---|
| Композиция экрана из компонентов библиотеки, их props и состояния | `shadcn-implementation-builder` |
| Формы: схемы валидации, submit, ошибки полей | `shadcn-implementation-builder` |
| Доступность и адаптивность собранных компонентов | `shadcn-implementation-builder` |
| Роутинг, стейт приложения, data fetching, интеграция с API | `frontend-developer` |
| Дизайн-токены, глобальные стили, темизация, анимации | `frontend-developer` |
| Кастомные компоненты вне библиотеки, инфраструктура фронтенда | `frontend-developer` |

Спорный случай решается в пользу `frontend-developer`. Код builder'а проходит тот же цикл ревью, что и любой другой.

Если такое разделение проекту не нужно — ставь три агента без builder'а, а его практики влей в `frontend-developer` (см. режим B ниже).

## Как интегрировать в проект — инструкция для кодингового агента

**Если ты — кодинговый агент, которому дали задачу «интегрируй агентов»,** сначала пройди основную инструкцию в корневом README (шаги 1–8). shadcn-агенты предлагай ТОЛЬКО после явного «да» на вопрос из шага 2: работает ли проект с shadcn/ui или другой registry-библиотекой готовых компонентов. Ответ «нет» → эту папку не трогаем вообще.

Получил «да» — выбери с пользователем режим.

### Режим A: отдельными агентами (когда UI строится на библиотеке систематически)

Подходит, когда почти каждый экран собирается из готовых компонентов и хочется дисциплины «сначала проверь библиотеку, потом пиши».

1. Скопируй агентов: `cp shadcn/shadcn-*.md <проект>/.claude/agents/`
2. Создай `docs/shadcn/` и положи туда `components-library-rule.md` и `registries.json`
3. **Заполни правило библиотеки вместе с пользователем** — это обязательный шаг, а не формальность. Спроси, какая библиотека основная (варианты — из `registries.json`; базовый shadcn/ui записывается как `@shadcn`). Без заполненного правила каждый агент будет переспрашивать при каждом запуске
4. Проверь MCP: подключён ли shadcn MCP (даёт агентам прямой доступ к реестрам). Не подключён — агенты работают на документации и командах CLI, это медленнее, но рабочий режим. Настройка — `npx shadcn@latest mcp` либо запись в `.mcp.json` проекта
5. **Проговори границу с `frontend-developer`** (таблица выше) и запиши её в `CLAUDE.md` проекта — иначе два агента будут спорить за одну и ту же работу
6. Проверь, инициализирован ли проект под shadcn (`components.json` в корне). Нет — предложи `npx shadcn@latest init`

### Режим B: влить практики в существующих агентов (когда четвёрка избыточна)

Подходит, когда библиотека используется эпизодически или команда не хочет плодить агентов. Тогда shadcn-агенты не ставятся, а их методология переносится секциями в УСТАНОВЛЕННЫЕ КОПИИ существующих агентов (исходный репозиторий не трогать!).

| Источник (shadcn/) | Целевой агент (установленная копия) | Что переносить |
|---|---|---|
| `shadcn-requirements-analyzer` | `designer` | Phase 2 (маппинг элементов на компоненты, приоритет готовым блокам, дерево иерархии) — в хендофф-часть |
| | `implementation-plan-architect` | Критерий «есть ли готовый блок в библиотеке» в проработку UI-задач плана |
| `shadcn-component-researcher` | `frontend-developer` | Phase 2 (проверка API по исходнику, поиск примеров несколькими паттернами, команда установки с реестром) — как раздел «Работа с registry-библиотекой» |
| | `researcher` | Специфика поиска по реестрам компонентов, если он ведёт выбор библиотеки |
| `shadcn-implementation-builder` | `frontend-developer` | Self-Review Checklist и «Типовые ошибки» — в его чек-лист; правило «сначала готовый блок, потом компонент, кастом последним» |
| `shadcn-quick-helper` | `frontend-developer` | Таблицу маппинга естественного языка на имена компонентов |
| `components-library-rule.md` | — | Ставится в `docs/shadcn/` в любом режиме: правило нужно и без отдельных агентов |

Правила переноса:
- Переносится методология (workflow-шаги, чеклисты, anti-patterns) — НЕ frontmatter, НЕ секции Agent Learnings (слаги останутся чужие), НЕ таблицы взаимодействий
- Секцию вставляй с заголовком-меткой источника, например `## Работа с registry-библиотекой (из shadcn-component-researcher)` — так её легко обновить при следующей синхронизации
- Правишь только копии в `<проект>/.claude/agents/` — исходный репозиторий остаётся универсальным

### Как выбрать режим

- **UI systematically собирается из библиотеки, важна дисциплина «не писать руками то, что есть готовым» → Режим A**
- **Библиотека используется точечно, состав агентов хочется компактный → Режим B**
- Смешивать можно: частый практичный вариант — поставить `shadcn-quick-helper` и `shadcn-component-researcher` отдельно, а практики builder'а влить в `frontend-developer`

## MCP

shadcn MCP опционален, как и все MCP в этом репозитории. Инструменты, которые используют агенты: `get_project_registries`, `search_items_in_registries`, `view_items_in_registries`, `get_item_examples_from_registries`, `get_add_command_for_items`, `get_audit_checklist`.

Без MCP каждый агент имеет прописанный фолбек: официальная документация библиотеки, `registries.json` как справочник URL, команды `npx shadcn@latest add`. Данные, полученные не из реестра напрямую, агенты помечают как требующие проверки.

## Learnings

У всех shadcn-агентов тот же механизм learnings, что у основного набора: читают `docs/agent-learnings/<имя-агента>/` перед работой, пишут при ошибках — если директория существует в проекте (см. шаг 6 корневой инструкции).
