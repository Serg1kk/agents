**Дополнительные разрешённые реестры:** —

**Правило приоритета:** компоненты из базового shadcn/ui берутся только тогда, когда подходящего компонента нет в основной библиотеке проекта.

## Главный принцип

При создании интерфейсов **ВСЕГДА** приоритетно использовать готовые компоненты из библиотеки вместо написания с нуля. Кастомная разработка допустима только в исключительных случаях, когда функционал не реализуется через существующие компоненты.

Порядок приоритета — строгий:

1. **Высший приоритет** — готовые блоки и секции библиотеки (hero, pricing, features, auth-формы, дашборд-лейауты)
2. **Средний приоритет** — отдельные компоненты для композиции
3. **Низший приоритет** — кастомные элементы, только при доказанной невозможности первых двух

## Пошаговый алгоритм

### 1. Анализ требований

- Требования обязательны до начала работы. Нет требований — собери их вопросами:
  - Тип проекта (лендинг, веб-приложение, мобильное приложение)
  - Целевая аудитория
  - Основные функции и разделы
  - Стилистические предпочтения
  - Брендинг и цветовая схема
  - Адаптивность и поддерживаемые устройства
- Убедись в полном понимании требований перед следующим этапом

### 2. Список необходимых компонентов

На основе требований — структурированный список всех UI-элементов по категориям:

- **Навигация**: меню, хлебные крошки, пагинация
- **Формы**: поля ввода, кнопки, чекбоксы, селекты
- **Контент**: карточки, списки, таблицы, модальные окна
- **Медиа**: галереи, слайдеры, превью изображений
- **Обратная связь**: уведомления, алерты, лоадеры
- **Макет**: хедер, футер, сайдбар, контейнеры

### 3. Исследование документации библиотеки

Для каждого компонента:

- Найти компонент в документации библиотеки, изучить варианты и модификации
- Скопировать примеры кода базового использования
- Определить возможности кастомизации (props, стили, variants)
- **ПРИОРИТЕТНО** искать готовые секции, покрывающие несколько требований разом, и оценить их адаптируемость

Зафиксировать: название компонента, ссылку на документацию, базовый пример, доступные варианты стилизации, необходимые props.

### 4. Планирование стилизации

- Определить дизайн-систему проекта (цвета, типографика, отступы) — при наличии `DESIGN.md` или `docs/design-system.md` она главнее дефолтов библиотеки
- Составить план адаптации компонентов библиотеки под стиль проекта
- Выбрать подходящие variants или спланировать кастомные стили через принятый в проекте стилевой инструмент
- Учесть брендинг

### 5. Реализация

1. Начинать с готовых блоков библиотеки
2. Адаптировать стилизацию под проект
3. Дополнять отдельными компонентами по необходимости
4. Минимизировать кастомный код

Принципы стилизации:

- Кастомизация — утилитарными классами / токенами, принятыми в проекте
- Сохранять структуру и логику работы оригинальных компонентов
- Держать консистентность по всему проекту
- Поддерживать адаптивность и доступность

## Когда кастомный компонент допустим

- Функционал полностью отсутствует в библиотеке
- Требования настолько специфичны, что адаптация готового компонента неэффективна
- Нужны уникальные анимации или интерактивность

Обязательные действия при создании кастома:

- Задокументировать причину отказа от готового компонента
- Следовать дизайн-системе библиотеки в стилях и поведении
- Обеспечить совместимость с остальными компонентами проекта

## Контроль качества

Перед финализацией проверить:

- [ ] Все возможные компоненты взяты из библиотеки
- [ ] Стилизация соответствует требованиям и брендингу
- [ ] Адаптивность работает корректно
- [ ] Доступность соблюдена
- [ ] Код оптимизирован и читаем
- [ ] Готовые блоки использованы там, где это возможно

## Запрещено

- ❌ Начинать работу без требований
- ❌ Писать компоненты с нуля без проверки библиотеки
- ❌ Игнорировать готовые блоки в пользу сборки из отдельных компонентов
- ❌ Пропускать этап изучения документации
- ❌ Нарушать структуру и логику работы оригинальных компонентов библиотеки
