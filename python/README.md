# Python-агенты

Language-специфичные агенты для проектов, где Python — ядро: AI-кор бэкенд, data-пайплайны, чистый Python-сервис. Они НЕ входят в обязательный пайплайн основного набора — это опциональное дополнение для Python-проектов.

| Agent | Роль |
|-------|------|
| `python-async-specialist` | Async-архитектура: asyncio/AnyIO, structured concurrency, отмена/таймауты, очереди и воркеры, дебаг гонок |
| `python-type-checker` | Типизация: mypy/pyright, постепенная миграция legacy, Protocol/TypedDict, Pydantic на границах, type-гейт в CI |
| `python-pytest-specialist` | Тестовая инфраструктура: фикстуры, parametrize, моки на границах, борьба с flaky, xdist, coverage-пороги |
| `python-performance-optimizer` | Перф Python-кода: профилирование (py-spy, scalene), GIL, векторизация, аллокации, замеры до/после |
| `python-data-analyst` | Данные: ETL-пайплайны, EDA, feature engineering, классический ML (sklearn) без утечек, воспроизводимость |

Все пять — самодостаточные файлы в формате `.claude/agents/` (frontmatter + промпт), как и основной набор.

## Как интегрировать в проект — инструкция для кодингового агента

**Если ты — кодинговый агент, которому дали задачу «интегрируй агентов» в Python-проект,** сначала пройди основную инструкцию в корневом README (шаги 1–8), затем реши, в каком режиме подключать Python-агентов. Режим выбирает пользователь — предложи ему один из двух и объясни разницу.

### Режим A: отдельными агентами (когда Python — ядро проекта)

Подходит, когда проект — это в первую очередь Python: AI-кор бэкенд, data-платформа, Python-сервис. Классического веб-бэкенда и фронтенда может не быть вовсе.

1. Скопируй нужных: `cp python/*.md <проект>/.claude/agents/` (или выборочно — см. шаг 3)
2. **Роль основного разработчика:**
   - Если в проекте есть обычная бэкенд-разработка (API, бизнес-логика) — оставь `backend-developer` из основного набора: он универсален и сам адаптируется под Python-стек. Python-агенты дополняют его специализациями.
   - Если проект — AI-кор (LLM-пайплайны, ML) — основным разработчиком становится `ai-engineer`, а Python-агенты закрывают его языковую специфику (async-инференс, типизация, тесты, перф, данные). `backend-developer` в таком проекте может быть не нужен — не ставь лишнего.
3. **Выбор состава по проекту:** нет data-работы → `python-data-analyst` не нужен; нет async → `python-async-specialist` не нужен; типизация и pytest нужны почти всегда.
4. Пайплайн ревью общий: код Python-агентов проходит тех же `code-reviewer` → `security-reviewer` → `qa-engineer`, git — только через `devops`.

### Режим B: влить практики в существующих агентов (когда отдельные агенты избыточны)

Подходит, когда Python — один из языков проекта или команда не хочет плодить агентов. Тогда Python-агенты не ставятся, а их методология переносится секциями в УСТАНОВЛЕННЫЕ КОПИИ существующих агентов (исходный репозиторий не трогать!).

Куда что ложится:

| Источник (python/) | Целевой агент (установленная копия) | Что переносить |
|---|---|---|
| `python-async-specialist` | `backend-developer` / `ai-engineer` | Секции Workflow Step 1–3 (когда async уместен, structured concurrency, sync/async-граница) — как раздел «Python Async» |
| | `implementation-plan-architect` | Критерий «async vs multiprocessing vs очередь» в проработку архитектуры |
| `python-type-checker` | `backend-developer` / `ai-engineer` | Step 2–4 (постепенная типизация, Pydantic на границах) — как раздел «Python Typing» |
| | `code-reviewer` | Пункты чеклиста: нет немотивированных `Any`/`# type: ignore`, структуры не через сырые dict |
| | `implementation-plan-reviewer` | Требование типизации/type-гейта в планах Python-проектов |
| `python-pytest-specialist` | `qa-engineer` | Step 2–5 (фикстуры, моки на границах, flaky, coverage) — в режим «автотесты» |
| `python-performance-optimizer` | `performance-engineer` | Step 2 (типовые Python-bottlenecks: GIL, векторизация, аллокации) — в раздел «Частые bottlenecks» + инструменты py-spy/scalene в контекст |
| `python-data-analyst` | `ai-engineer` | Step 1–3 (EDA, сплиты без утечек, baseline-first) — в раздел про данные |
| | `database-engineer` | Принцип «агрегируй в SQL, не тяни сырьё» и витрины для аналитики |

Правила переноса:
- Переносится методология (workflow-шаги, чеклисты, anti-patterns) — НЕ frontmatter, НЕ секции Agent Learnings (слаги останутся чужие), НЕ таблицы взаимодействий.
- Секцию вставляй с заголовком-меткой источника, например `## Python Async (из python-async-specialist)` — так её легко обновить при следующей синхронизации.
- Правишь только копии в `<проект>/.claude/agents/` — исходный репозиторий остаётся универсальным.

### Как выбрать режим

- **Python-ядро, интенсивная работа с async/данными/перфом → Режим A** (отдельные агенты, точечные вызовы).
- **Python вторичен или команда хочет компактный состав → Режим B** (обогащение копий).
- Смешивать можно: например, отдельный `python-pytest-specialist` + перф-практики влиты в `performance-engineer`.
