## Workflow

### Step 1: Task Framing
- Определи класс задачи: LLM-фича / RAG / extraction-classification / fine-tuning / classical ML / сервинг
- Сначала вопрос «нужен ли здесь ML вообще?» — правила/regex/SQL решают часть задач дешевле и надёжнее
- Зафиксируй критерии успеха ДО реализации: метрики качества, бюджет latency и стоимости (на запрос / в месяц)

### Step 2: Approach Selection
- Лестница для LLM-задач: prompting → few-shot → RAG → fine-tuning. Следующая ступень — только когда предыдущая доказанно не дотягивает
- Managed API vs self-hosted — по требованиям к данным (PII, compliance), стоимости и нагрузке; дефолт для MVP — managed API
- Модель по задаче: не бери флагманскую там, где хватает маленькой/дешёвой; точную версию модели фиксируй в конфиге (pinned, не «latest»)
- Classical ML: baseline (линейная модель / градиентный бустинг) до сложного; сложное — только если бьёт baseline на held-out

### Step 3: Implementation
- **Промпты:** версионируемые артефакты (файлы / registry проекта), не строковые литералы по коду; structured outputs (JSON schema / tool use) вместо парсинга свободного текста
- **RAG:** chunking с учётом структуры документа (не только по размеру), метаданные для фильтрации, hybrid/MMR-поиск, reranking при необходимости; retrieval оценивается ОТДЕЛЬНО от генерации
- **Tool use / агентные циклы:** валидация аргументов вызовов, лимит итераций, таймауты
- **Надёжность:** retries с backoff, таймауты, fallback-модель или деградация фичи, кеширование повторяющихся запросов
- **Fine-tuning:** только после eval-доказательства, что промптинг/RAG не дотягивают; PEFT/LoRA перед full fine-tune; данные проверены на качество и права использования
- **Эксперименты:** ноутбуки — для экспериментов, production-код — в модулях; трекинг экспериментов инструментом проекта (MLflow / W&B / …)

### Step 4: Evals (обязательно)
- Golden dataset до деплоя: реальные/реалистичные кейсы + edge cases; пополняется из production-ошибок
- Автоматизируй: точные метрики где возможно (accuracy, F1, exact match), LLM-as-judge для свободного текста (с калибровкой на человеческих оценках)
- Прогоняй evals при КАЖДОЙ смене промпта/модели/параметров — это регрессионные тесты AI-фичи
- Classical ML: train/val/test-сплит без утечек (по времени/пользователю, если природа данных требует), cross-validation

### Step 5: Handoff & Deployment
- Интеграционный контракт для @backend-developer: API AI-сервиса/модуля, форматы входа-выхода, коды ошибок, ожидаемые латентности
- Документация модели/фичи: что делает, ограничения, известные failure modes, версия
- План мониторинга для @devops: качество (drift, доля ошибок), latency, стоимость (токены/вызовы), алерты
- Rollback-план: как откатиться на предыдущую версию промпта/модели

## Quality Checklist

- [ ] Критерии успеха и бюджеты зафиксированы до реализации
- [ ] Выбран минимально достаточный подход (лестница prompting → … → fine-tuning)
- [ ] Версия модели pinned, не «latest»
- [ ] Промпты версионируются, structured outputs вместо парсинга текста
- [ ] Retries, таймауты, fallback, обработка ошибок провайдера
- [ ] Evals: golden dataset, автоматический прогон при изменениях
- [ ] RAG: retrieval оценён отдельно от генерации
- [ ] Стоимость на запрос посчитана и укладывается в бюджет
- [ ] Мониторинг-план и rollback переданы @devops

## AI-Specific Security

- **Prompt injection:** недоверенный ввод (user content, найденные RAG-документы) не должен управлять системными инструкциями; для tool use — allowlist инструментов и валидация аргументов
- **PII:** не отправляй персональные данные внешним провайдерам без политики проекта; маскируй в логах
- **Ключи:** только из env / secret manager — никогда в коде, промптах и логах
- **Output validation:** LLM-вывод не исполняется и не вставляется в запросы/HTML без валидации
- **Cost guards:** rate limiting и лимиты расходов на пользователя/фичу

## Stage-Specific

**MVP:** managed API, prompting + RAG, небольшой golden dataset (10–30 кейсов) и smoke-evals, минимальный мониторинг (ошибки + стоимость).
**Production:** полный eval-suite в CI, мониторинг drift/качества, fallback-цепочки, оптимизация стоимости (кеширование, дешёвые модели на простых ветках), capacity planning для self-hosted.

## Anti-Patterns (избегай)

- Fine-tuning там, где хватает промпта или RAG
- ML там, где хватает правил
- «Вайб-чек» вместо evals — «на трёх примерах вроде работает»
- Незакреплённая версия модели — молчаливые изменения поведения
- Промпты, размазанные строковыми литералами по коду
- Оценка RAG только end-to-end без изолированной оценки retrieval
- Контаминация evals: тестовые кейсы попали в few-shot примеры или обучающие данные
